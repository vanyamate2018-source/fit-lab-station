# Камеры, профили и управление

Это целевая архитектура. Реализованные части и ограничения отмечены в `PROGRESS.md`.

## Независимые устройства

CameraDevice хранит идентичность камеры, модель, версию прошивки и актуальные capabilities.
RadioLink хранит передатчик, RX1/RX2, Link ID, параметры радиоканала и ссылку на ключ.
FlightController хранит вариант/версию MSP, состояние UART и полученную телеметрию.
Замена камеры не пересоздаёт приёмники или полётник. IP является текущим адресом, не идентичностью.

## Расширение без изменения приложения для каждой модели

Драйвер реализует протокол: OpenIPC/Majestic, ONVIF, RTSP или отдельный vendor API.
Профиль JSON описывает совпадение family/model/firmware/soc/sensor/radio_driver, название и ограничения возможностей.
Профили находятся в `/Volumes/FIT-LAB/data/config/camera-profiles/`.
Новый профиль не может добавить протокол, выполнение shell-команд или неподтверждённую возможность записи.
Для нового закрытого протокола нужен новый проверенный драйвер; для модели с существующим протоколом обычно достаточно профиля.

Сейчас работают обнаружение RTSP-кандидата, OpenIPC SSH, чтение схемы Majestic и
проверяемая запись поддерживаемых параметров. По радио проверены чтение и смена FPS
с чтением результата; радио SSH использует тот же закреплённый SSH host key, что LAN.
При привязке OpenIPC читаются SoC, сенсор, VERSION_ID и драйвер Wi-Fi. Профиль выбирается по фактически полученным полям; отсутствующая модель не угадывается. На стенде получены ssc33x, imx415, VERSION_ID 2024.02.10 и rtl88x2eu. Совпадение профиля не разрешает неподдерживаемые записи.

Пример формата (условная модель, не заявленная совместимость):

```json
{
  "schema": 1,
  "id": "example-camera",
  "label": "Example camera",
  "driver": "openipc_ssh",
  "match": {"family": "openipc", "model": "example-model"},
  "capabilities": ["video.parameters.read"]
}
```

## Прямое подключение

LAN → обнаружение кандидата → подтверждение идентичности и вход → чтение возможностей → привязка.
UI строится по данным камеры: кодеки, разрешения, FPS, bitrate, GOP, ISP, доступные OSD-модули.
Если прошивка не сообщает диапазоны и разрешённые значения, универсальный редактор не угадывает их;
остаётся чтение и существующая панель прошивки. RTSP сам по себе предоставляет видео, а не универсальную настройку камеры.

Для изменения: проверить возможности и диапазон → сохранить прежние значения на SSD → отправить минимальное изменение →
прочитать фактический результат → подтвердить восстановление видеопотока. Смена кодека согласуется с декодером.
Смена частоты требует отдельной согласованной операции передатчик/RX1/RX2 и заранее проверенного пути восстановления.
Недоступная камера не должна получать накопленные команды автоматически при возвращении связи.

## Радио туда и обратно

Цель: два RX принимают одну камеру и передают пакеты общему декодеру с устранением дублей и FEC.
Обратные короткие команды передаёт один выбранный адаптер; одновременная передача обоих не предполагается.
TX на Mac уже проверен: WFB 160 вверх / 32 вниз, контрольные ответы и SSH к камере.
Сейчас передаёт RX1; переноса роли на RX2 нет. Реализованы ID операций, поколение подключения, срок очереди 15 с и отмена отложенных команд при разрыве. Чтение по закреплённому SSH может завершиться после краткой потери echo; запись после потери связи не переотправляется. Радиотранзакции имеют отдельную квитанцию на камере.
Факт принятия команды подтверждается чтением результата с камеры. Отсутствие ACK показывается как неподтверждённое состояние.
Для API нужен работающий IP-туннель либо камерный агент. Наличие `wfb_rx` на неизвестном UDP-порту не доказывает готовый API.
Приоритеты: видео и необходимые служебные сообщения; затем ограниченные по частоте настройки.
Влияние TX на соседний RX и общее эфирное время проверяются на стенде до включения в обычном режиме.

WFB-NG поддерживает IP-туннель и двустороннюю телеметрию. Текущая FIT-LAB сборка
уже выполняет RX+TX, но локальный IP relay пропускает только контрольный echo и SSH;
полётная телеметрия отдельным потоком ещё не подключена.
Источник: [WFB-NG](https://github.com/svpcom/wfb-ng).
Актуальный план следующего этапа: [TX и управление](tx-control.md).

## Ключи

Ключи относятся к паре/группе связи, не к названию модели. Два приёмника одной камеры используют одну привязку декодера.
WFB-файлы сторон содержат собственный закрытый ключ и открытый ключ противоположной стороны; это не просто одинаковый пароль.
Новая физическая камера той же модели не гарантирует совпадение ключей.
Можно provision несколько камер в одну группу, но общие ключи расширяют доступ на всю группу;
одновременные передатчики с одинаковым Link ID/портом создадут конфликт потока.
Целевой вариант — отдельная связка профиля и ссылки на ключ для каждой камеры, без ключевого материала в JSON/журнале/Git.
Текущий рабочий ключ не перевыпускался; его уникальность относительно заводских ключей не проверялась.
Разделение мастер/приёмник, сценарий добавления и замены камеры, хранение ключей
и условия отката описаны в [проекте привязки](pairing.md). Это проектирование,
а не уже доступная автоматическая генерация.

## OSD и задержка

MSP DisplayPort передаёт команды отрисовки OSD. Для числовых карточек полётных данных нужен отдельный согласованный MSP-парсер;
нельзя выдавать элементы видеокартинки за полученную телеметрию. Версия INAV/Betaflight определяет команды, шрифты и сетку.
Камерный OSD, полётный OSD и уведомления станции — разные слои. Уведомления FIT-LAB находятся вне видео.
Источник: [Betaflight DisplayPort](https://betaflight.com/docs/development/API/DisplayPort),
[OpenIPC MSPOSD](https://github.com/OpenIPC/msposd).

Задержка зависит от сенсора, кодирования, GOP/FEC, очередей, декодера и дисплея.
Основной просмотр и запись используют исходный сжатый поток. Трансляция не должна заставлять основной просмотр перекодировать видео.
RTSP и отдельный WebRTC relay реализованы. Браузерный relay перекодирует в H.264/30 FPS независимо от основного просмотра. Его качество при потерях требует отдельной проверки.
Источник: [GStreamer jitterbuffer](https://gstreamer.freedesktop.org/documentation/rtpmanager/rtpjitterbuffer.html),
[MediaMTX browser playback](https://mediamtx.org/docs/read/web-browsers).

Текущая документация OpenIPC рекомендует получать возможности из конкретной сборки камеры:
[Majestic integration](https://github.com/OpenIPC/dashboard/blob/main/docs/MAJESTIC.md).

## Мастер подготовки камеры по LAN (проектирование 25.09)

Последовательность экранов: «Камера» → «Видео» → «Радиолиния» → «Привязка» → «Проверка».
Один итоговый экран показывает изменения перед применением; неизменённые настройки не записываются.

- Камера: аппаратная идентичность, сенсор, SoC, сборка прошивки, доступные API; привязка к SSH host key.
- Видео: кодек, разрешение, FPS, bitrate и GOP из возможностей конкретной сборки. Кодек приёмника следует выбранному профилю.
- Радиолиния: обнаруженные Wi-Fi адаптер/драйвер, диапазон, канал/частота, ширина, MCS/FEC, доступное управление мощностью.
- Мощность: показывать единицы драйвера. mBm = 100 × dBm; индекс усилителя не является dBm или мВт.
  Пересчёт индекса в мВт допустим только с подтверждённой таблицей конкретного модуля. Не переносить пределы RTL8812EU на RTL8812AU.
  На проверенном rtl88x2eu применяется `iw` без остановки WFB; результат сверяется с драйвером, YAML и vendor INI.
- Частота: двухфазная радиооперация prepare → arm → перестройка RX → проверка видео и значений → commit.
  На камере действует 40-секундный откат без commit. Переключение 5540 → 5500 → 5540 МГц и
  мощность 20 → 9 dBm подтверждены через RF; LAN не использовался для этих команд.
  Ширина канала пока не вынесена в редактор. Частота и мощность находятся справа на главном экране.
- Привязка: «Использовать текущую» по умолчанию для уже работающей камеры; «Создать новую пару» отдельным действием.
  `wfb_keygen` запускается в новой приватной папке с правами 0700, файлы 0600. Никогда в папке действующей пары.
  `gs.key` остаётся на станции, `drone.key` передаётся конкретной подтверждённой камере по проверенному защищённому каналу (SFTP на текущей камере не прошёл проверку).
  До успешной проверки сохранить рабочую пару и возможность отката. Логи содержат ID операции, не ключевой материал.
- Новая камера такой же модели — новая идентичность: предложить заменить камеру в существующей привязке или создать отдельную.
  Автоматическая генерация ключей при каждом подключении запрещена: это разорвёт уже работающую радиолинию.
- Проверка: обе стороны применили профиль, RX1/RX2 принимают, ключ подтверждён реальной расшифровкой, есть RTP/кадры.

Генерация и установка новых ключей остаются проектом. Частота и мощность проверены по RF на этой камере; это не универсальная поддержка других радиодрайверов. Нужны длительный прогон и дополнительные аварийные сценарии.

Первичные источники:

[OpenIPC: управление мощностью BL-M8812EU2](https://github.com/OpenIPC/wiki/blob/master/en/fpv-bl-m8812eu2-wifi-adaptors.md),
[OpenIPC: конфигурация Majestic](https://github.com/OpenIPC/wiki/blob/master/en/majestic-config.md),
