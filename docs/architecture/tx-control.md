# FIT-LAB — управление по обратному каналу

Проверка кода и первичных источников: 25.09.2026. Реализация и оставшиеся этапы; радиооперации на стенде проверены отдельно от планов.

## Что уже есть

| Возможность | Фактическое состояние |
|---|---|
| Обратный канал | WFB stream 160 вверх, 32 вниз; RX1 одновременно принимает и передаёт, RX2 принимает видео |
| Проверка связи | Echo с nonce раз в секунду, RTT, истечение статуса через 3 с без ответа |
| Управление камерой | SSH через локальный relay, закреплённая идентичность камеры, пароль только в памяти |
| Настройки изображения/видео | Схема конкретной прошивки, минимальная запись, чтение результата, резервная копия изменяемых полей |
| Проверенная запись по радио | FPS 60 → 30 → 60; это не проверка всех полей прошивки |
| Частота/мощность | RF prepare/arm/commit с 40-секундным откатом на камере; 5540 → 5500 → 5540 МГц и 20 → 9 dBm подтверждены по радио |
| Адаптация | В сохранённом профиле камеры найден `/usr/bin/alink_drone`; в диагностике не работал. Версию и совместимость ещё проверить |
| Полётник | msposd есть, получение настоящих данных INAV/Betaflight пока не подтверждено |

Основание: `receiver/control_link.py`, `receiver/resilient_radio.py`,
`master/camera_api.py`, `master/camera_radio.py`, `master/camera.py`,
`shared/control_packets.py`, сохранённые проверки в `/Volumes/FIT-LAB/data/exports/`.
Echo подтверждает путь туда и обратно, но не факт применения настройки и не свежесть видеокадра.
Сохранённые диагностические снимки не считаются текущими значениями камеры.

## Приоритет 1 — понятные команды и подтверждённое состояние

Один диспетчер операций для ручного управления, будущего «Авто» и восстановления.
Для каждой команды: ID, идентичность камеры, поколение соединения, ожидаемая версия
настроек, срок действия, запрошенное значение, фактическое значение и результат.
Состояния: отправляется → проверяется → применено; отдельно «не подтверждено» и «отменено».
Успех требует чтения фактического значения; потерянный ответ не является доказательством отказа.
Повторять неидемпотентную операцию вслепую нельзя. Для повторов с тем же ID нужен
журнал уже выполненных операций на камере; текущий SSH сам по себе его не предоставляет.

Реализовано: `CameraRequest` с ID, поколением и сроком очереди 15 с. Смена камеры, транспорта или потеря связи отменяет отложенную запись; поздний результат не применяется к другому подключению. Журнал связывает запрос с readback, транспортом и результатом. Пароли/ключи не записываются. Краткий пропуск echo не отменяет уже выполняющийся запрос по закреплённому SSH: он завершается в пределах собственного тайм-аута, без автоматической повторной записи. Смена камеры/транспорта по-прежнему инвалидирует такой запрос.

Одинаковые повторные чтения объединяются. Запись может заменить ожидающее чтение,
но не прерывает текущую операцию и не вытесняет другую запись. Во время активного
запроса UI не запускает фоновое обновление и не разблокирует редактор по событию
возврата echo. Журнал отдельно сохраняет `queue_ms`, `execution_ms`, `elapsed_ms`.

Осталось:
- Профиль камеры хранит общее `control_ready=false` и `video.parameters.read`, хотя
  реальная запись уже реализована. Возможности должны зависеть от драйвера, прошивки,
  текущего транспорта и конкретного поля: read / live-write / reload / LAN-only.
- После запуска приложения настройки требуют входа. Возможность «Запомнить вход» —
  отдельное согласие пользователя и хранилище системы, а не пароль в JSON на SSD.

Экран «Управление»: транспорт, камера, выбранный адаптер TX, свежесть ответа, RTT,
доля ответов за скользящее окно, последняя команда. Цвет связи и цвет результата команды
не подменяют друг друга. Уведомления находятся за пределами видеокадра.

## Приоритет 2 — мощность без перезапуска видео

Разделить «Мощность передатчика камеры» и «Мощность обратного канала станции».
У Mac сейчас фиксированный индекс 10 в запуске bridge; это не 10 dBm и не 10 мВт.
У RunCam отдельные значения драйвера, WFB и vendor INI. Нельзя переносить таблицу
другого Wi-Fi модуля или считать прочитанную мощность измерением излучения.

На rtl88x2eu проверено применение `iw` без остановки WFB. Vendor INI, WFB YAML и
фактические значения драйвера сверяются. Мощность также проходит согласованную
операцию с readback/commit; неподтверждённое изменение откатывается камерой.
Результат не переносится автоматически на другие платы и драйверы.

## Приоритет 3 — «Авто» с запасом по пропускной способности

OpenIPC Adaptive-Link передаёт оценку связи на борт, где выбирается профиль;
потеря обратной связи вызывает заранее заданный fallback. Есть задержки переходов
и гистерезис, чтобы профили не менялись от каждого скачка RSSI.
[Документация OpenIPC](https://docs.openipc.org/use-cases/fpv/wfb-ng/install-adaptive-link/).

Для нашей системы предлагается первый этап: фиксировать канал, полосу, кодек и FPS,
адаптировать только проверенный диапазон битрейта. Затем отдельно добавить MCS/FEC
и мощность, когда подтверждены методы применения без перезапуска и совместимость RX.
При ухудшении снижать нагрузку быстрее, чем повышать при улучшении; конкретные
пороги выбрать по стендовым данным, а не перенести из чужого модуля.

Сигналы для решения: потери после FEC, нагрузка восстановления FEC, SNR/RSSI каждого
живого RX, пакеты/байты, свежесть статистики, локальные пропуски кадров и ответы TX.
Просадка FPS из-за GUI/декодера не доказывает плохой эфир. Сильный RSSI тоже сам по
себе не доказывает чистый канал. Отдельно учитывать uplink и downlink.
Сначала режим наблюдения: записывать предполагаемый профиль, ничего не менять.
Потом ограниченное применение и проверка влияния на задержку.

Обычные SSH-операции сейчас занимают секунды: они читают схему, проверяют и сохраняют
настройки. Для частой адаптации нужен совместимый компактный heartbeat/API, а не
новая SSH-сессия на каждый отсчёт. Существующий relay допускает только echo и SSH;
ALink потребует отдельно реализованного и ограниченного по типам/частоте транспорта.
Не запускать установщик ALink поверх vendor-конфигурации до проверки версии и конфликта владельцев.
В примерах upstream команды IDR различаются; поддержка запроса ключевого кадра именно
на этой Majestic-сборке пока не подтверждена.
[Исходный проект Adaptive-Link](https://github.com/OpenIPC/adaptive-link).

## Приоритет 4 — резервирование TX

Оба адаптера продолжают принимать одну камеру; видео объединяется по пакетам,
переключать целую картинку между приёмниками не требуется.
Передаёт только один владелец TX. При отключении RX1 роль может перейти на RX2;
возвращение RX1 не должно тут же вызывать обратное переключение.
Нужны подтверждение остановки прежнего передатчика, удержание выбранного владельца,
границы попыток и журнал причин переключения. Скачки RSSI не повод менять TX.

Сейчас RX2 стартует в режиме RX-only, а control stream 32 получает только RX1.
Просто переименовать «RX2 → TX» в UI недостаточно. Нужны приём ответов с обоих адаптеров
с устранением дублей и динамическое включение передачи в native bridge без повторной
инициализации единственного оставшегося RX. Если аппаратный путь требует перезапуска,
его перерыв видео необходимо измерить и явно учитывать.

## Приоритет 5 — частота с автоматическим возвратом

Удалённая смена частоты должна быть транзакцией на камере и приёмной станции.
Борт сначала сохраняет старый профиль и запускает независимый таймер отката,
подтверждает готовность и выполняет согласованный переход. Станция переводит оба RX,
подтверждает свежий ответ камеры и восстановление декодированного видео; лишь затем
отправляет commit. При отсутствии commit борт сам возвращается на прежний канал,
даже когда SSH и радиосвязь уже пропали. Станция также возвращается по таймеру.

ID транзакции, конечные сроки и повторное подтверждение должны переживать обрыв
соединения; потеря commit-ответа разрешается чтением состояния операции. Камерный watchdog уже реализован в `master/radio_switch.py`, локальная незавершённая операция сохраняется на SSD. Реальный тест без ACK подтвердил возврат на старый канал. Ошибка применения драйвером проверена изолированным тестом: возвращаются сохранённый и рабочий каналы. Полная матрица частичной записи, перезапуска борта и исчезновения USB ещё не закрыта.
Автовыбор частоты начать со сканирования до запуска видеоприёма и рекомендации канала.
Во время приёма не уводить оба RX на сканирование. Любое использование RX2 для сканирования
временно убирает diversity и требует отдельного явно выбранного режима.

## Телеметрия, OSD и будущие модули

INAV/Betaflight: сначала UART и MSP/DisplayPort, затем отдельные числовые значения
с отметкой времени и исчезновением устаревших данных. OSD-команды рисования не равны
полной телеметрии. Одним UART управляет один сервис с согласованной пересылкой,
несколько независимых читателей не должны забирать байты друг у друга.
В MSPOSD есть пересылка MSP по UDP, а MSPVTX обозначен upstream как alpha;
его нельзя считать уже готовым способом настройки нашей камеры.
[OpenIPC MSPOSD](https://github.com/OpenIPC/msposd).

WFB поддерживает двусторонний MAVLink, но это отдельный транспорт/протокол;
он не появляется автоматически из работающего SSH. Для выбранных INAV/Betaflight
начать с подтверждённого MSP. Управление стиками/CRSF потребует отдельного пути
с измеренной задержкой и поведением при потере связи, а не очереди настроек камеры.
[WFB-ng MAVLink](https://github.com/svpcom/wfb-ng/wiki/Mavlink-mode).

На будущем SBC-приёмнике разместить RadioLink, TX-владельца, watchdog и диспетчер
операций; мастер-пульт работает через LAN API. Закрытие интерфейса не должно обрывать
видеоприём или отменять обязательный откат на борту. Драйверы WFB, SDR и CRSF должны
сообщать собственные возможности, состояние и единицы измерения. Общее имя раздела — «Модули».

## Условия проверки следующей реализации

1. Команда либо подтверждена чтением, либо явно остаётся неподтверждённой; повтор не
   исполняет её второй раз. Просроченная команда не применяется после возвращения камеры.
2. Разрыв TX не блокирует декодирование и запись; выдерживается бюджет служебного трафика.
3. Вынутый RX1 не уничтожает живой поток RX2; перенос TX проверен без непрерывных переключений.
4. Пропавшая связь после изменения радиопрофиля возвращает обе стороны на исходные параметры.
5. «Авто» сравнивается с фиксированным профилем при одинаковых условиях по потерям,
   качеству, частоте смены режима и измеренной задержке, а не только по RSSI.
6. Перед дальнейшим заявлением о стабильности — длинный прогон, сквозная задержка
   камера → экран, проверка одновременной записи/трансляции и настоящей телеметрии.

## Уточнения повторной проверки

Повтор ARM того же ticket после утраты ответа распознаёт начатую операцию.
Квитанция done:0 проверяется по текущему драйверу, WFB и vendor-конфигурации.
Ошибки save_failed/apply_failed/stop_timeout возвращают явный отказ и свежие
параметры, вместо бесконечного pending. После исчерпания поиска каналов остаётся
доступным «Обновить» для повторного ограниченного поиска; изменения не переотправляются.
Незавершённая квитанция на SSD сохраняется до подтверждённого исхода.

На работающем стенде проверен отдельный сбой процесса каждого RX: около 2,5–2,7 с
до восстановления, оставшийся RX продолжает видео, RX1 временно теряет TX.
Это не подтверждение физического hotplug и не резервирование TX.
По новому запросу пользователя мощность камеры на канале 108 сохранена 20 dBm
(максимум, сообщаемый драйвером), а прежние измерения на 9 dBm остаются отдельными.

Перезапуск vendor-службы также сверяет FPS, кодек и битрейт с обоими user.ini
до остановки процессов. Реально обнаружено расхождение 60/30 FPS между памятью
и SD, исправлено штатной записью по радио; повторный перезапуск сохранил 60 FPS.
Во время этой проверки пользователь затем выбрал 5220 МГц и 1920×1080/60 FPS.
